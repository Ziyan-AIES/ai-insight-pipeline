### 2.1 P1/P2 建议执行批次

“任务”仍是最小实现和验收单位；“批次”只把同一依赖链、同一发布面或同一测试环境的任务排在一起。每完成一个编号就保留可审查结果，前一项不通过时不继续依赖它的下一项。单批主动工作控制在约 1–3.5 小时，数据库 migration、Web 部署、GitHub 推送和 Chrome Web Store 提交分别记录，外部等待不计入主动工作时间。

## 3. P0：先关闭凭证发送风险

**目的与范围：**修 F01；限 `extension/shared.js`、`content.js`、`background.js` 及相关回归测试。不修改 Radar、不重做全部登录流程。

**执行步骤：**

2. 把 workspace 判定改成受信配置的精确 origin 比较。开发 localhost 仅从明确开发配置进入，不能依靠页面提交的新地址获得信任。

**交付/发布：**本地补丁与测试证据；需商店新包，交给 T02/T03。不能声称服务器更新能修复用户已安装的旧 JS。

### T02 — 对齐已发布基线并制作安全补丁包

**目的与范围：**明确哪一个完整插件包将发布，保留可追溯证据。

**执行步骤：**
1. 查证开发者后台或实际安装版本，记录版本号、unlisted 状态和商店 ID；无法取得包/版本就明确留缺项，不默认等于 0.4.6。

3. 根据实际商店版本确定更高的新版本，更新 manifest 和相应版本断言；不要预先固定一个可能已被使用的版本号。
4. 从受控提交或可追溯源树生成完整 ZIP，根目录直接包含 manifest；记录源 revision、文件列表、ZIP SHA-256、变更说明。

## 4. P1：保护编辑、登录和核心交互

### T05 — 编辑回写检查导出版本

**目的与范围：**修复“模型处理期间人工修改，被旧结果覆盖”；只处理版本冲突，租约和字段锁分别交给 T25/T26。

**执行步骤：**
1. 追踪 `scripts/run-local-editorial.ts` 导出 → 输出校验 → `editorial-sync.mjs` → `apply_editorial_sync`，确认当前 version 的更新时机。
2. 导出时携带 news ID 和 version；版本来自可信队列快照，不依赖模型生成，提交时按 URL/ID 重新关联。
3. 新增 migration，使回写按 ID/URL 加 expected version 条件更新；不匹配时不写任何编辑字段，返回可识别的冲突结果。
4. 明确批次策略：本次先采用整批冲突回滚并提示重新导出，避免一半成功却整批重试；保留 run 失败/冲突记录。
5. 更新 runner/API 校验和测试：正常提交、处理期间改动、缺失版本、被删记录、相同结果重试。

**验收：**导出后改标题，再提交旧 AI 结果，标题及其他人工字段保持原样；调用方收到冲突，不能提示成功。

**交付/发布：**migration、runner/API 补丁和回归测试；采用兼容的分阶段部署，先准备 DB 新能力，再升级调用方，最后收紧版本要求。旧 runner 不能静默绕过保护。

**状态（2026-09-08）：**B05 实现已进入 `main`；Phase 1 migration 已应用生产。runner 从 claim 快照注入 ID/version/run UUID/lease owner；guarded RPC 在整批写入前检查版本和归属，冲突返回 409，同请求可幂等重试。Phase 3 仍按部署手册暂缓，需先完成受控生产回写验证。

### T25 — 编辑回写检查租约与任务归属

**目的与范围：**避免旧 runner 清掉新 runner 的租约或覆盖其结果；与 T05 分开实现。

**执行步骤：**
1. 记录 claim、run ID、lease owner、expires_at、release 的全部数据库路径。
2. 为回写/释放携带可信任务标识，校验提交任务与当前租约归属；不得由模型决定归属。
3. 新增条件更新，旧租约失效或被重新领取后拒绝旧提交；只释放本任务持有的记录。
4. 让冲突、完成、失败三条路径按归属清理，避免失败处理误清其他任务。

## 7. 发布与任务交接模板

Web、Functions、DB 和插件有不同到达时间。凡接口变化均记录：先部署什么、旧客户端如何工作、新能力如何探测、如何回退。后续插件功能版复用 T02/T03 的流程，但使用新的版本记录；不把 P0 发布记录改写成后来功能版记录。

推荐直接把以下内容作为每次工作的任务说明：

> 执行 `docs/implementation-plan-2026-09-07.md` 的 **Txx**（有子编号则写完整）。先确认仓库、工作区和依赖，只完成该任务范围。补相应行为回归测试，运行相关检查。结束时报告修改、验证、未完成验收与发布需求。此轮不附带执行其他任务；提交/推送/部署按本会话已有授权处理，未授权则交付可审阅结果。

每项交付记录：

| 字段 | 要填写的内容 |
|---|---|
| 状态 | 未开始 / 实现中 / 本地通过 / 待外部验收 / 完成 |
| 基线 | HEAD、相关线上版本、已有无关改动 |
| 改动 | 文件、行为、DB/API 兼容规则 |
| 验证 | 实际命令和结果；mock、真实浏览器、线上证据分开 |
| 发布 | Web / Functions / DB / 商店，以及先后顺序 |
| 剩余项 | 审核等待、权限缺失、尚未验证内容 |
